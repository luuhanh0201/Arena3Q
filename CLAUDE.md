## Project state

Arena3Q is a Unity **6000.6.6f1** project (2D URP template) with a playable PvE prototype: Attack and Defense stages, hero summoning, squads, commands, camera and HUD with placeholder art, hero levels / stars / factions, hero skills (passive, auto-cast skills, rage ultimates), and the game flow (intro → login → server → lord select → name → opening story → tutorial battle). The startup scene is `Assets/Arena3Q/Scenes/Frontend.unity` (the game flow), which hands the battle to `Assets/Arena3Q/Scenes/Battle.unity`; Battle can still be played on its own in the Editor (it then uses the stage's test loadout). The template's `Assets/Welcome/` and `Assets/Scenes/SampleScene.unity` were moved out of the repo to `D:\UnityProjects\Arena3Q_Archive_2D` (2D-only files are archived there, not deleted; see its README).

**Current direction (2026-10-21): 3D presentation.** Battle uses the Universal Forward renderer (index 1), a tilted orthographic camera and direct skinned models. The 2D-template description above is project history. Read `docs/KeHoach/ChuyenSang3D.md` §12: ground is XY at z=0, world up is −Z, logic remains Vector2. Work split since 06:40: Codex makes Mặc Ảnh and Lữ Bố (and Claude reviews them), Claude makes the non-hero rest of the conversion (see `AgentComms/STATUS.md`); validate in Unity for now, Android build/device testing is deferred by the user. Do not claim the device performance gate has passed.

**Code must stay easy to change later** (user request): numbers, lists and content live in ScriptableObjects (never hard-coded), pure rules in Core, and anything that will be replaced (accounts, server list, profile storage, intro video) sits behind an interface with a prototype implementation.

The gameplay specification lives in `docs/GameplaySpecification.md` (tracked in git as lowercase `docs/`; on Windows `Docs/` is the same folder, so never create a second copy with different casing) and is the source of truth for gameplay. Read it before designing or writing gameplay code. Its markers: ✅ settled (implement exactly), 🟡 provisional default (must be a config option), ⏳ deferred (not in the prototype). If it conflicts with the configuration below (e.g. 3D, legacy input), flag the conflict instead of silently picking one.

## Key configuration

- **Rendering:** URP, Battle uses Universal Forward via `BattleViewConfig`. Models use URP-compatible materials, one directional light and ambient with blob shadows. Flipbook VFX retain billboard/ground layers and need a Forward-compatible pass. Renderer2D and the old sprite route remain only while migration is unfinished; do not validate the 3D path using the old route.
- **Input:** `activeInputHandler: 1` means the **new Input System only**. The legacy `UnityEngine.Input` API will throw at runtime; use `UnityEngine.InputSystem`. A default action asset exists at `Assets/Settings/InputSystem_Actions.inputactions` (`Player` map: Move, Look, Attack, Interact, Crouch, Jump, Previous, Next, Sprint; plus a `UI` map), but the battle does not use it: `BattleInputController` reads `Mouse.current` and `EnhancedTouch` directly, and the HUD's `InputSystemUIInputModule` uses its built-in default actions.
- **Frame rate:** at least **60 FPS** on every platform (spec §1, user decision 2026-10-21). Unity on Android runs at 30 unless `Application.targetFrameRate` is set, so the game sets 60 from data at startup (no 30 option); re-measure FPS on the device (avg / p95, full battle workload) after any graphics or VFX change. Flipbook VFX blend adjacent frames on the effect / battle clock; character sprites do not blend.
- **Target platforms:** Android, iOS and PC, landscape orientation (per the spec). Only an `Android Dev` build profile exists so far, in `Assets/Settings/Build Profiles/`; Android uses the IL2CPP scripting backend. Input must work with both touch and mouse.
- **Packages** (`Packages/manifest.json`): 2D Animation, Aseprite and PSD importers, Tilemap + Tilemap Extras, SpriteShape, Timeline, uGUI, Visual Scripting, Test Framework.

**Rules:** all project rules and lessons logs live in `docs/QuyTac/` (index `docs/QuyTac/README.md`); the user's standing working rules for every agent are in `docs/QuyTac/QuyTacLamViec.md`. In-game UI rules (no em/en dashes, no Unicode emoji or symbol icons, icons only from dedicated icon libraries, minimal formatting) are in `docs/QuyTac/ThietKeUI.md`; they cover text and icons shown to the player (HUD, Frontend, content assets), not docs or chat. Bugs fixed so far, with root causes and how to avoid repeating them, are logged in `docs/QuyTac/NhatKySuaLoi.md`. Read it before changing gameplay code or running batch builds/tests, and add an entry for every bug you fix.

For all 3D model, skinning, animation and VFX work, read and follow `docs/QuyTac/Model3D_Rules.md` before editing. Surface deformation and visual checks are mandatory; passing transform-only tests does not authorize delivery. Every wrong direction, error or bug met during that work (any agent) goes **at once** into `docs/QuyTac/NhatKyVanHanh_3D.md` (what happened, root cause, how it was found, the prevention rule; user request 2026-10-21); read it before starting such work.

## Code layout

All game code is under `Assets/Arena3Q/Scripts`, one asmdef per folder, dependencies flowing one way: Core ← Data ← Gameplay ← UI ← Frontend, with Editor on top.

- **Core** (`Arena3Q.Core`): pure C# rules, no MonoBehaviours. `BattleRuntimeState` (all per-battle state, new instance per battle), commands (`SummonRequest`, `MoveCommand`, `AttackCommand`) validated by `SummonRules` / `CommandRules`, `BattleOutcomeRules` + `StarRating`, and the brains: `HeroBrain` (the spec §6 state machine), `TroopBrain`, `EnemyBrain`. Brains read the world through sensor interfaces (`IHeroSensor`, ...) and return a `HeroIntent` (Hold / MoveTo / Engage), which keeps them unit-testable.
- **Data** (`Arena3Q.Data`): ScriptableObjects (`HeroDefinition`, `TroopDefinition`, `StageConfig`, `TestLoadout`, `FactionDefinition`) with `Validate()` and converters to Core settings (`StageConfig.CreateBattleSetup`, `CreateHeroBrainSettings`). Every 🟡 rule is a field here.
  - **Progression** (`Data/Progression`, rules in `Core/Progression`): `ProgressionConfig` (levels, stars, lord skill unlocks and points, breakthroughs, crit, damage-reduction cap), `GrowthProfile` (per-class growth), faction synergy tiers on `FactionDefinition`. Hero stats in the assets are the level-1 / 1-star values; `CombatNumbersFactory` is the only place that turns a `LineupEntry` (hero + level + stars) into the numbers a unit fights with. Balance invariants (equal growth product, equally strong lords at every level) are EditMode tests in `ProgressionContentTests`.
  - **Skills** (spec §3 "Kỹ năng trên thẻ"): each hero has 4 `SkillDefinition` assets (`Data/Skills`; slot 0 passive, 1–2 auto-cast, 3 ultimate) built from data blocks (targeting, shape, zone, repeats, caster move, effects / passives), so a new skill is a data change. `Content/Skills/<hero>/` is generated by `SkillContentBuilder` from `docs/Tuong/*.md`. Rules in `Core/Skills` (`StatusSet`: timed statuses, no stacking; `RageMeter`; `SkillMath`). In battle `HeroUnit.Skills` (`Gameplay/Skills/HeroSkills`) runs passives, auto-cast (2 before 3), cast wind-up and rage; `SkillTargetingResolver` / `SkillExecutor` / `SkillZone` aim and apply. Statuses live on every `UnitBase` (`Statuses`, `ApplyStatus`, `Displace`); the player's ultimate goes through `BattleController.TryUseUltimate`. Blocks added for Lữ Bố (any hero can use them): `PassiveKind.FrenzyStacks` (`FrenzyMeter` in Core: a stack per attack instance, +damage per stack, lifesteal and slow immunity at full), `SkillEffectKind.KnockUp` (`StatusKind.Airborne`: cannot act, lifted on an arc) and `FrenzyStacks` (with `minimumTargets`), a per-skill execute bonus, `CasterMove.LeapToPoint`; his assets come from **Arena3Q > Lu Bu > Build Skills** (`LuBuSkillsBuilder`).
  - **Enemies** (spec §8, docs/QuanDich): `EnemyDefinition` (subclass of `TroopDefinition`: tier, body radius, skills, boss `PhaseTwo`, `flying`, revive) and `EnemySkillDefinition` (aim, red-warning time, first-use cooldown, channel, summons / clones) in `Data/Enemies`; both skill kinds share `SkillAreaDefinition` (area, zone, effects). Content in `Content/Enemies/C1..C3` from `EnemyContentBuilder` (also the boss stages `Stage_Attack_C1_Boss`, `Stage_Defense_C3_Boss`). Rules in `Core/Enemies/EnemyTypes.cs` (`EnemyRules`). In battle `EnemyUnit.Skills` (`Gameplay/Skills/EnemySkills`) runs warning → effect → channel; phase 2, revive and taunt/anti-lock live on the units; flyers path over `BattlefieldLayout.ForFlyers()`; the HUD shows a boss bar.
- **Gameplay** (`Arena3Q.Gameplay`): `BattleController` is the composition root and the only entry point for player actions; `UnitBase` subclasses (`HeroUnit`, `TroopUnit`, `EnemyUnit`, `CastleUnit`) implement the sensors and execute intents; `UnitRegistry` does spatial queries; `BattleInputController` (mouse + touch gestures, tap interpretation in `BattleController.TapAt`) and `BattleCameraController`. Sprites are generated at runtime by `PlaceholderArt`.
  - **Logic vs view positions:** gameplay runs on a flat logic plane. `UnitBase.Position` is the logic position; `transform.position` is only its on-screen projection (`BattleController.ToView`). Never read `transform.position` for gameplay, and convert screen ↔ battlefield only through `BattleCameraController.ScreenToWorld` / `WorldToScreen` / `WorldToViewport` (in 3D a ray down to the ground z = 0, `TiltedViewMath` in Core). Ground decorations go through `AddGroundVisual`.
  - **3D presentation** (`BattleViewConfig`, loaded from `Content/Resources/BattleView.asset`; `Presentation3D` off = the old flat squash): the ground is the logic plane XY at z = 0, up = −Z, and the camera is orthographic, turned about X by `viewTiltDegrees` (the painted art's 41.4°) on the Universal renderer (`BattleView3D`: camera, sun, flat ambient, no realtime shadows). `ToView` does not squash in 3D (`ViewYScale` = 1; `GroundProjection` = cos(tilt) is what the screen shows; `ToScreenPlane` is the old view space the camera pans in). Upright pictures face the camera (`UprightRotation` on unit roots, pillars, decor, castle fall, VFX upright layers via `IMacAnhBillboard`); ground pieces get the inverse rotation; offsets "up on screen" use `ScreenUp`, heights use `WorldUp`. Units without art stand as `UnitBody3D` capsules (Simple Lit, blob shadow, facing, hit flash); map props are 3D models from `MapProps3DLibrary` (`Art/Maps/batQuaiTran/Props3D/`, **Arena3Q > Build 3D Map Props**, same size / pivot / yaw as their sprites, which stay as disabled data references); the painted ground lies on `Ground3DView` (mesh, shader `Arena3Q/Ground 3D`: flat under the units, low hills outside the map bounds, drawn first without depth). Heroes with a `HeroModel3D` (`HeroModel3DView`) or Mặc Ảnh's direct mode show the real skinned model. `Logs/RenderStats.json` (`RenderBudgetTests`) counts triangles and draw calls of a full battle against the plan's budget.
  - **Forbidden zones** are `IObstacle`s (`RectObstacle`, `RiverObstacle`: centre line + width, passable only at crossings; `CircleObstacle`; `WallObstacle`: a thick segment that can be switched on and off, after which the switcher calls `BattlefieldLayout.RebuildRoutes`) and block movement: `UnitBase.MoveTowards` follows `BattlefieldLayout.NextWaypoint` (shortest route over a visibility graph of nodes precomputed around the zones) with `ResolveStep`/`PushOut` as a safety net. Stage data: `StageConfig.forbiddenZones` (rects), `rivers` and `formation`.
  - **Bát Quái Trận** (the current map of every stage, docs/BanDo/BatQuaiTran.md): rules in `Core/Map/BaguaFormation.cs` (`BaguaFormation`: 8 pillars, 8 gates whose type rotates clockwise every 20 s, slabs that close Đỗ gates, altar capture and blessing; `BaguaGateVisits`: once-per-entry triggers and per-unit cooldowns); data in `BaguaFormationConfig` (`Data/Maps`, geometry imported from `BatTran_Layout.json`); one runtime formation per battle, whose obstacles are in `BattleController.Layout` (`StageConfig.CreateLayout(formation)`). In battle `BaguaFormationRunner` (`Gameplay/Stages`) ticks it after movement, rebuilds routes and pushes caught units out when a slab switches, applies gate effects (`Heal`, `MoveSpeedUp` / `Slow` statuses, true damage via `TakeDamage(..., ignoreReduction: true)`); `BaguaFormationView` draws it; castles show `CastleConfig.art` (`CastleArtConfig`: intact + destroyed sprite, fall animation numbers) and `CastleFallView` plays the fall (real time, so after the battle ends; the HUD result screen waits `BattleController.ResultDelaySeconds`); `MapDecorView` draws `StageConfig.decorations` (`MapDecorConfig`, pictures only); dev keys F5 / F6 / Shift+1..8 (Editor and Development builds) call `BattleController.DevRotateFormation` / `DevCycleAltarOwner` / `DevToggleGate`.
  - **Rendered heroes** (3D models rendered to 8-direction sprites in Blender; sources and scripts under `docs/art/concepts/<Hero>/`, to move out of docs once the user approves each hero): Lữ Bố uses `HeroAnimationSet` + `HeroAnimationView` (docs/Tuong/LuBu.md; import `LuBuContentBuilder`, 2048 atlas pages). Mặc Ảnh (look of `lord_strategist`) uses `MacAnhPerformance` (clips, sockets, skill bindings, effects; `MacAnhPerformanceView`, `MacAnhCombatPerformance` with one cast clock and `CastEventGate`, `MacAnhProjectiles`, battle-scoped `MacAnhFxPool`); production notes in `docs/art/concepts/MuuSi_main-hero/MacAnh/Production/Delivery_QA.md`. A realtime 3D trial sits behind `MacAnhPerformance.enableBattle3DTrial` (off).
  - **VFX come from existing packs first** (user 2026-10-22; rule in `docs/QuyTac/QuyTacLamViec.md` §3): a store / free particle effect is used as it is, then adapted (colour, timing, size, the hero's style). `ThirdPartyVfxBuilder` (**Arena3Q > Mac Anh > Third Party**) upgrades its materials with URP's `ParticleUpgrader`, wraps the original prefab (turned Y-up → up = −Z, play on awake off) with `MacAnhFx` + `ParticleFxPresenter` (battle clock via `Simulate`, sized to the skill radius, colour fade) and lists it in `MacAnhPerformance.thirdPartyEffects`; `Effect(key)` prefers it and falls back to the own effect when its files are missing, `OwnEffect(key)` skips it. Store files live in `Assets/ThirdParty/`, which is git-ignored (Asset Store EULA; the repository is public). Skill01 Huyền Cơ Trận currently plays Hovl Studio's free "Magic circle 2". Building effects from scratch (the flipbooks below) is only for when no pack fits; the agents' main job is now fitting each hero's motion to its skills and checking carefully for errors.
  - **Mặc Ảnh battle VFX are flipbooks**: frames rendered by `docs/art/concepts/MuuSi_main-hero/MacAnh/vfx_macanh_flipbooks.py` (Blender; `--only`, `--out` for a staging folder, `--preview`), imported by **Arena3Q > Mac Anh > Graphics > Import and Bind Flipbook VFX to Battle** (`MacAnhFlipbookBuilder`) into `MacAnhVfxRecipe` assets (layers: frames, plane, charge/release phase, timing, fades, scale, spin, glow, underlay, qi breath/dissolve, `screenDim`) played by `MacAnhVfxPlayer` through `IMacAnhSpatialEffect`; shader `Arena3Q/MacAnh Flipbook 2D` (premultiplied light + underlay, drifting density noise, noise dissolve). Effects disperse with `MacAnhFx.FadeOut` (hit, end of flight, charge handed to the release). Wind and smoke must never be periodic helix bands or evenly spaced lines (`docs/QuyTac/Model3D_Rules.md` lines 28–29). Sprite atlases and flipbook pages are not committed (only code and small assets, user decision 2026-10-20).
- **UI** (`Arena3Q.UI`): `BattleHud` builds the uGUI HUD from code (cards with skill icons, cooldowns and rage bar – `HeroCardView`: tap = ultimate, drag = aimed ultimate, hold 1.5 s = select; timer, edge icons, result screen); `UiFactory` (public) holds the shared uGUI helpers.
- **Frontend** (`Arena3Q.Frontend`, the game flow of docs/KeHoach/VaoGame.md): `FrontendController` (Frontend scene) shows one screen at a time (`Screens/`: intro, login, server, lord select, name, story) in the order of `FrontendConfig.steps`; `FrontendFlowPlanner` (Core) skips screens a returning player does not need. Services sit behind Core interfaces in `FrontendServiceLocator`: `IPlayerProfileStore` (prototype: `JsonFileProfileStore`, tests: `InMemoryProfileStore`), `IAccountService` (prototype: `OfflineAccountService`, guest only), `IServerDirectory` (prototype: the `ServerList` asset). Content assets in `Data/Frontend` (`FrontendConfig`, `LordRoster`, `ServerList`, `LordNameConfig`, `StoryScript`). `FrontendConfig.developmentLordLevel` (15) lets Development players on a device fight with every lord skill (they unlock at levels 2/5/10/15); not the Editor (use **Arena3Q > Mac Anh > Play Combat Test**), not release. The battle is handed over with `BattleLaunch` (Gameplay): stage + lineup + result callback; `BattleController` picks it up in `Start`, otherwise it plays its own stages with the test loadout.
- **Editor** (`Arena3Q.Editor`): `PrototypeContentBuilder` (+ `FrontendContentBuilder`) creates the placeholder assets in `Assets/Arena3Q/Content`, the Battle and Frontend scenes and the build scene order (only missing assets; empty scene references are filled; delete an asset to regenerate it) and adds the menu items `Arena3Q > Build Prototype Content / Validate Stages / Open Battle Scene / Apply Standard River Layout` (a river map; the shipped stages now use the Bát Quái Trận); `MapBlueprintExporter` (`Arena3Q > Export Map Blueprints`) rasterises each stage from its data into `docs/art/blueprints`. `PropSpriteRenderer` (`Arena3Q > Render Prop Sprites`, settings in `PropSpriteRenderConfig` assets) renders 3D prop models into sprites in the fixed 3/4 view (PPU 128, soft ground shadow, pivot = ground centre) through a CommandBuffer and `Hidden/Arena3Q/PropCapture`, without touching the 2D Renderer; `MeshyAssetPostprocessor` sets first-import options for `Meshy_AI_*` files, which are gitignored sources (only the sprites are committed). `BatQuaiTranMapBuilder` (`Arena3Q > Apply Bat Quai Tran Map`, also run at the end of Build Prototype Content) imports the formation geometry from the layout JSON, renders missing slab sprites and puts formation, painted ground (`backgroundArtArea` = its rim area) and castles on every stage. `BuildScripts` has the build methods (`Arena3Q > Build`).
- **Tests**: `Assets/Arena3Q/Tests/EditMode` (Core/Data rules) and `Tests/PlayMode` (`BattleFlowTests` drives the real Battle scene with `BattleController.Simulate`; it uses `SerializedObject`, so the file is wrapped in `#if UNITY_EDITOR`). Do not make the PlayMode asmdef Editor-only: the runner would treat it as EditMode tests. ## Working in this repo

- Unity generates `.csproj`/`.slnx` files and everything under `Library/`, `Temp/`, `Logs/`, and `UserSettings/`. Don't edit these by hand; they're gitignored or regenerated.
- Every asset under `Assets/` needs its `.meta` file committed alongside it. When creating, moving, or deleting assets outside the Editor, keep the `.meta` file in sync (moving it with the asset keeps its GUID, so scene and prefab references survive).
- Scenes, prefabs, and `.asset` files are YAML referencing GUIDs/fileIDs. Avoid hand-editing them except for trivial, well-understood changes.
- New gameplay code should live in its own assembly definition so it compiles separately from other assemblies. Tests need a separate test asmdef that references `UnityEngine.TestRunner`/`UnityEditor.TestRunner` (Test Framework 1.8).

## Command-line build and test

Everything runs through the Unity Editor executable (normally installed via Unity Hub at `C:\Program Files\Unity\Hub\Editor\6000.6.6f1\Editor\Unity.exe`). The project must not be open in another Editor instance while these run.

```powershell
$unity = "C:\Program Files\Unity\Hub\Editor\6000.6.6f1\Editor\Unity.exe"

# Run EditMode tests (use -testPlatform PlayMode for play mode tests)
& $unity -batchmode -projectPath . -runTests -testPlatform EditMode -testResults Logs/test-results.xml -logFile -

# Run a single test or fixture
& $unity -batchmode -projectPath . -runTests -testPlatform EditMode -testFilter "Namespace.ClassName.MethodName" -logFile -

# Compile-check scripts without building
& $unity -batchmode -quit -projectPath . -logFile -

# (Re)create missing placeholder content and the Battle scene
& $unity -batchmode -quit -projectPath . -executeMethod Arena3Q.Editor.PrototypeContentBuilder.BuildAll -logFile -

# Builds (output under Builds/, gitignored)
& $unity -batchmode -quit -projectPath . -executeMethod Arena3Q.Editor.BuildScripts.BuildAndroidDev -logFile -
& $unity -batchmode -quit -projectPath . -executeMethod Arena3Q.Editor.BuildScripts.BuildWindowsDev -logFile -
```

In batch mode, `-logFile -` output is easy to lose; writing to `Logs/<name>.log` and grepping for `error CS` works better.

**After every player build, tell the user how big the app is**, in MB with one decimal (MB = bytes / 1 048 576, the same unit as the `[Arena3Q] Build …` log line from `BuildScripts`): Android = size of the `.apk` in `Builds/Android/`, Windows = total size of `Builds/Windows/` (excluding the `*_BurstDebugInformation_DoNotShip` / `*_BackUpThisFolder_ButDontShipItWithYourGame` folders). Compare with the previous build when known; the last Android dev build (2026-10-16) was 40.2 MB.

To open the Editor straight into the battle: `Start-Process $unity -ArgumentList '-projectPath "<repo>"', '-executeMethod Arena3Q.Editor.PrototypeContentBuilder.OpenBattleScene'`.

Starting a player build makes Unity rewrite `Assets/Settings/UniversalRP.asset` (shader prefiltering), `UniversalRenderPipelineGlobalSettings.asset` and `ProjectSettings/UnityConnectSettings.asset`; don't commit those side effects together with feature work.
